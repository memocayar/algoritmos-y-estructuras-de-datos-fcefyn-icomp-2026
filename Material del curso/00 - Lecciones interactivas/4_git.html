// explicación detallada

La teoría, para alguien que arranca ahora

¿Qué problema resuelve un control de versiones?

Sin Git, "versionar" un proyecto termina siendo una carpeta con proyecto_final.zip, proyecto_final_v2.zip, proyecto_final_v2_DEFINITIVO.zip. Git hace lo mismo pero de forma automática, estructurada y compartida: cada cambio queda registrado con quién lo hizo, cuándo, y por qué (el mensaje de commit) — y varias personas pueden tener su propia copia trabajando en paralelo sin pisarse.

Repositorio local y remoto

Un archivo modificado en tu compu pasa por tres etapas antes de llegar al equipo:

Directorio de trabajo
git add →
Área de staging
git commit →
Repositorio local
git push →
GitHub (remoto)

git add elige qué cambios entran al próximo commit. git commit los guarda en tu historial local, con un mensaje. git push recién ahí los sube al remoto, donde el resto del equipo los puede bajar con git pull.

Ramas (branches)

Trabajar siempre directo sobre main es la forma más rápida de romper el proyecto de todos. Una rama es una línea de desarrollo independiente: podés experimentar, romper cosas, hacer commits a medio terminar, y main ni se entera hasta que decidís unir (merge) esa rama de vuelta.

Merge y conflictos

Un conflicto de merge pasa cuando dos ramas modificaron la misma línea del mismo archivo de formas distintas — Git no puede adivinar cuál de las dos versiones querés, así que te lo deja resolver a mano. No es un error: es lo esperable cuando varias personas tocan el mismo código.

Pull Requests y revisión de código

Un Pull Request (PR) no es solo "avisar que subiste cambios" — es pedir que alguien del equipo revise ese código antes de que se una a main. Un buen checklist de PR, como el que usamos en el proyecto integrador, incluye:

CHECKLIST DE PR
  • ¿Compila sin warnings?
  • ¿El mensaje de commit explica el por qué, no solo el qué?
  • ¿Sigue las convenciones del proyecto (PascalCase, m_, override, etc.)?
  • ¿Alguien más del equipo lo revisó antes del merge?

rebase vs merge

git merge une dos ramas creando un commit de merge que preserva ambas historias tal como pasaron. git rebase en cambio "reescribe" tu rama como si hubieras empezado a trabajar recién después de los últimos cambios de main — el resultado es un historial más lineal y prolijo, a costa de que los commits originales cambian de identidad (hash). Por eso el rebase es genial en tu propia rama, y peligroso en una rama compartida.
