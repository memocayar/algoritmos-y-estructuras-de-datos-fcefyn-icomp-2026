// explicación detallada

La teoría, para alguien que arranca ahora

¿Qué es una clase? Cómo modelar una, paso a paso

Una clase es un molde que junta los datos de una entidad (sus atributos) con lo que esa entidad puede hacer (sus métodos). Modelar una clase no es adivinar — es un proceso de tres pasos que podés aplicar siempre:

PASO 1 — IDENTIFICAR LA ENTIDAD

Un sustantivo del problema que tiene identidad propia.

"un Nodo del diagrama"
PASO 2 — ATRIBUTOS: ¿QUÉ TIENE?

Los datos que necesita guardar para existir.

id, etiqueta, posición (x, y)
PASO 3 — MÉTODOS: ¿QUÉ HACE?

Las acciones que puede realizar con esos datos.

mover(), renombrar(), dibujar()

Con esos tres pasos, "Nodo" deja de ser una idea vaga y se convierte en algo concreto: una clase con atributos m_id, m_etiqueta, m_posX, m_posY, y métodos como mover() y dibujar().

Constructor y destructor

El constructor es el método especial que corre automáticamente en el instante en que un objeto nace — se usa para dejar el objeto en un estado válido desde el primer momento (nunca "a medio hacer"). El destructor es su contraparte: corre automáticamente cuando el objeto deja de existir, y se usa para liberar lo que ese objeto haya reservado (memoria dinámica, archivos abiertos, lo que sea).

class Nodo { public: Nodo(int id, std::string etiqueta) // constructor : m_id(id), m_etiqueta(etiqueta) { } ~Nodo() { } // destructor };

private, protected, public

Encapsular no es "esconder por esconder": es decidir qué parte de una clase es su contrato con el resto del programa, y qué parte es un detalle interno que podés cambiar sin romper nada afuera.

  • private — solo la propia clase lo puede tocar. Es el detalle interno.
  • protected — la propia clase y sus clases derivadas lo pueden tocar. Es lo que compartís con quien herede de vos.
  • public — cualquiera lo puede tocar. Es el contrato hacia afuera.

En los diagramas de clases, esto se anota con símbolos delante de cada atributo o método: + para public, - para private, # para protected — los vas a ver así en el diagrama de la próxima sección.

Herencia

Nodo y Conexión son distintos, pero se parecen: ambos tienen un id, una posición, y necesitan poder dibujarse. En vez de repetir eso en cada clase, se lo damos a una clase base común — ElementoDiagrama — y Nodo y Conexión heredan de ella con : public ElementoDiagrama. Así es como se ve ese diseño en un diagrama de clases real:

«abstracta»
ElementoDiagrama
#m_id : int
#m_posX, m_posY : int
+ElementoDiagrama(id : int)
+virtual ~ElementoDiagrama()
+virtual dibujar() = 0
Nodo
-m_etiqueta : string
+Nodo(id, etiqueta)
+dibujar() override
Conexion
-m_origen : Nodo*
-m_destino : Nodo*
+Conexion(id, origen, destino)
+dibujar() override

El triángulo hueco es la notación estándar de "herencia" en UML: apunta siempre hacia la clase base. Fijate que Conexion guarda Nodo* — un puntero, no una copia — exactamente lo que vimos en el módulo 1.

Polimorfismo: virtual y virtual puro

Un método virtual tiene una implementación en la clase base, pero permite que cada clase derivada la reemplace con la suya — y en tiempo de ejecución se llama a la versión que corresponde al objeto real, no al tipo del puntero.

Un método virtual puro (se escribe agregando = 0; al final) va un paso más allá: la clase base ni siquiera da una implementación. Declara que "toda clase derivada TIENE que implementar esto", pero no dice cómo. Una clase con al menos un método virtual puro se vuelve abstracta: no se puede instanciar directamente — nunca vas a poder escribir ElementoDiagrama e;, porque no tiene un cuerpo para dibujar(). Solo podés crear objetos de sus clases derivadas concretas (Nodo, Conexion), que sí lo implementan.

Diagramas de secuencia

Mientras el diagrama de clases muestra la estructura (qué clases hay y cómo se relacionan), el diagrama de secuencia muestra el comportamiento en el tiempo: qué objeto le manda un mensaje a cuál, en qué orden. Cada objeto es una línea vertical (su "línea de vida"), y el tiempo corre de arriba hacia abajo. Así se ve, en su forma más simple, la construcción de un Nodo:

:Nodo :ElementoDiagrama │ │ │── ElementoDiagrama(id) ──────▶│ (arranca la base) │ │ │◀───── (base construida) ─────│ │ │ │── m_etiqueta = etiqueta │ (Nodo termina) │ │

Vas a ver esta misma secuencia construirse en vivo en la próxima sección.

Diagrama entidad-relación (DER)

Si en vez de pensar en código pensás en cómo vas a guardar esto en una base de datos, usás otra herramienta: el diagrama entidad-relación (DER). Se parece al diagrama de clases en que también identifica entidades y atributos, pero no tiene métodos, ni herencia, ni polimorfismo — solo estructura de datos y las relaciones entre entidades, con su cardinalidad (cuántos registros de un lado se pueden relacionar con cuántos del otro).

EL MISMO CONCEPTO, DOS MODELOS

"Nodo" se modela distinto según para qué lo necesitás: como clase (con comportamiento: dibujar(), mover()) para el código, y como entidad (solo datos, sin métodos) para la base de datos que va a persistir los diagramas guardados.

Al destruirse, el orden se invierte: primero corre ~Nodo(), y recién al final ~ElementoDiagrama(). Por eso el destructor de la base tiene que ser virtual — ver 04_galeria_fallas.

¿Y si el método es virtual puro?

Con dibujar() = 0; en ElementoDiagrama, la clase deja de ser instanciable. Probalo:

class ElementoDiagrama { public: virtual void dibujar() = 0; // virtual PURO };
error: no se puede declarar una variable de tipo abstracto 'ElementoDiagrama' porque el método virtual puro 'dibujar' no tiene implementación ↳ solución: instanciar Nodo o Conexion, que sí implementan dibujar()
