// explicación detallada

La teoría, para alguien que arranca ahora

¿Qué es un TAD?

Un Tipo Abstracto de Datos es un conjunto de valores y de operaciones definidos mediante una especificación independiente de cualquier representación. La manipulación de un TAD depende solamente de su especificación — nunca de su implementación.

Ejemplo simple: una puerta. Lo único que te importa desde afuera es que se puede Abrir(), Cerrar(), y consultar si EstaAbierta(). No necesitás saber si por dentro guarda un booleano, un entero, o un string para representar su estado.

Interfaz vs implementación

Separamos siempre estas dos cosas:

Declaración
QUÉ dice que hace
interfaz — vs —
Definición
CÓMO lo hace
implementación

La interfaz es un contrato entre quien implementa el TAD (Alan) y quien lo consume (Bárbara). Uno de sus objetivos centrales es enmascarar la implementación concreta: Bárbara solo trabaja con las primitivas que la interfaz expone, nunca con código que dependa de cómo Alan las armó por dentro. Por eso las interfaces no tienen constructores — no se pueden instanciar directamente, solo se accede a ellas a través de una función que devuelve una implementación concreta.

Primitivas e invariantes

Cada primitiva de un TAD se especifica respondiendo tres preguntas: ¿qué recibe?, ¿qué hace?, ¿qué devuelve? Una invariante es una condición que esa primitiva garantiza — por ejemplo, la invariante de Abrir() es "luego de aplicar Abrir(), el estado de la puerta será abierta". Las invariantes son las que forman las precondiciones y postcondiciones de cada primitiva, y las que un corrector automático (o vos mismo) van a verificar sin mirar nunca tu implementación interna.

¿Qué es la complejidad de un algoritmo?

Es una forma de describir cuántos recursos consume un algoritmo — típicamente tiempo y espacio. Nos importa para comparar implementaciones distintas de un mismo TAD, y para predecir el comportamiento cuando el input crece, sin tener que esperar a que realmente crezca en producción.

Medir tiempo real de ejecución depende de la computadora y de la implementación — no sirve para predecir. Contar operaciones básicas una por una es tedioso y ambiguo. Por eso usamos complejidad asintótica (Big O): contamos operaciones en función del tamaño del input, tomando siempre el peor escenario posible, y buscamos una cota superior.

Cómo calcular complejidad, paso a paso

Contás las operaciones en función de n y simplificás con estas cuatro reglas:

REGLAS PRÁCTICAS
  • Se desprecian las constantes que suman o restan: O(n + 2) = O(n)
  • Se desprecian las constantes que multiplican o dividen: O(2·n) = O(n)
  • Nos quedamos con el término más pesado: O(n² + n + 2) = O(n²)
  • Siempre revisar si la complejidad resultante tiene sentido

Ojo con los bucles anidados con límites distintos: recorrer una matriz de n filas por m columnas es O(n·m) — solo se simplifica a O(n²) si n es igual a m.

Notación formal: O, Ω y Θ

O(g(n)) es una cota superior: decimos que T(n) = O(g(n)) si existe una constante c y un n₀ tal que, para todo n ≥ n₀, T(n) ≤ c·g(n). Ω(g(n)) es una cota inferior: la misma idea, pero T(n) ≥ c·g(n). Θ(g(n)) significa ambas cosas a la vez — una cota ajustada por arriba y por abajo.

Complejidad de la recursividad y Teorema Maestro

Una función recursiva que se llama a sí misma dividiendo el problema se puede describir con una ecuación de recurrencia de la forma T(N) = A·T(N/B) + O(N^C), donde A es la cantidad de llamados recursivos, B la proporción en la que se divide el problema, y O(N^C) el costo de dividir y combinar (fuera de las llamadas recursivas). El Teorema Maestro resuelve esta ecuación comparando log_B(A) contra C:

log_B(A) < C
→
O(N^C)
log_B(A) = C
→
O(N^C · log N)
log_B(A) > C
→
O(N^log_B(A))

Lo vas a usar en vivo en la próxima sección con búsqueda binaria, MergeSort y un clásico: StoogeSort.
