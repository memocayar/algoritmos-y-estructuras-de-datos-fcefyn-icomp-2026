01

Punteros y referencias

Ejemplos/00_Punteros_Introduccion.cpp · Ejemplos/01_Punteros_Swap.cpp · Material Practico → 01_punteros

Una variable normal (int x = 5;) guarda un valor. Un puntero guarda una dirección de memoria: la ubicación donde vive otra variable. &x te da esa dirección; *p te da el valor que hay en esa dirección (lo que en clase se llama “desreferenciar”).

Analogía

Pensá una variable normal como una caja con un valor adentro. Un puntero es un papelito que en vez de tener el valor, tiene la dirección de la caja. Si dos papelitos tienen la misma dirección, los dos “apuntan” a la misma caja — cambiar el contenido desde uno se ve desde el otro.

En 01_Punteros_Swap.cpp ya se ve la razón de ser de esto: swap0(int a, int b) recibe copias, así que intercambiar a y b adentro de la función no cambia nada afuera. swap1(int *a, int *b) recibe las direcciones reales, así que *a = *b sí modifica las variables originales del main. Esa diferencia — “¿estoy tocando una copia o el original?” — es la primera pregunta que te vas a hacer todo el cuatrimestre.

Por qué importa acá: el struct pattern del proyecto (DynamicArray) documenta explícitamente que las referencias que devuelve se invalidan si el buffer interno se reubica en memoria. Guardar un puntero “crudo” a un guardia dentro de una lista de guardias es exactamente el tipo de bug que un puntero colgante (apuntando a memoria que ya no es válida) puede producir.

En el issue

Cada GuardSquadMember necesita saber a quién avisar: sus “vecinos”. La tentación es guardar un puntero directo a cada guardia vecino. El problema es que el GuardSquad va a guardar a todos los guardias en una lista propia — y si esa lista crece y se reubica en memoria, cualquier puntero que apuntaba “directo” a un guardia queda apuntando a memoria vieja. Por eso conviene que cada vecino se guarde como índice (un número de posición, int) dentro de la lista del escuadrón, no como puntero al objeto. Un índice no se “invalida” cuando la lista se reubica.

02

Clases para agrupar datos relacionados

Ejemplos/02_Estructuras_Fecha_Persona.c · Ejemplos/04_POO_Objeto_Tiempo.cpp

Un guardia tiene varios datos que viajan siempre juntos: su nivel de alerta actual y la lista de a quién puede avisar. En vez de tener variables sueltas, se agrupan en un tipo propio — una class o struct — igual que 04_POO_Objeto_Tiempo.cpp agrupa hora, minuto y segundo en un solo tipo Tiempo en vez de tres variables sueltas por ahí.

Ejemplos/04_POO_Objeto_Tiempo.cpp
// la idea, no el código completo del ejemplo
class Tiempo {
  public:
    void estableceHora1(int);
    int  obtieneHora1();
  private:
    int hora;
    int minuto;
    int segundo;
};

Lo mismo aplica a GuardSquadMember: en vez de tener, en algún lado suelto, “el nivel de alerta del guardia 3” y por separado “los vecinos del guardia 3”, un solo tipo agrupa ambos datos y viaja junto por todo el programa.

En el issue

El diagrama de clases del issue ya te da la forma exacta: GuardSquadMember con nivelDeAlerta y vecinos, y GuardSquad con la lista completa de miembros más el método propagarAlerta(origen, nivel). Es el mismo patrón que Tiempo, aplicado a un dato distinto.

03

Herencia y polimorfismo

Ejemplos/Clase 02 2024 Herencia.cpp · Material Practico → 02_poo

El proyecto ya tiene dos “formas de ser guardia”: StandardGuardStrategy y AlertedGuardStrategy. Ambas heredan de una misma interfaz, IGuardBehaviorStrategy, que declara un método sin cuerpo (virtual int decideDamage(...) const = 0; — el = 0 lo hace “puro”, es decir, obligatorio de implementar en cada clase hija). El resto del código llama siempre a decideDamage(...) sin saber ni importarle si el guardia es estándar o alertado — cada objeto “sabe” resolver la llamada a su manera. Eso es polimorfismo.

Analogía

Es como pedir “hacé ruido” a distintos animales. El que pide no necesita un if por cada animal — cada uno ya sabe cómo responder a “hacé ruido” a su manera. La interfaz es la promesa de que todos entienden ese pedido; cada clase hija decide cómo cumplirlo.

include/cybercba/combat/GuardBehaviorStrategy.hpp (ya existe en el repo)
class IGuardBehaviorStrategy {
  public:
    virtual ~IGuardBehaviorStrategy() = default;
    virtual int decideDamage(const CombatState& state) const = 0;
};

class StandardGuardStrategy final : public IGuardBehaviorStrategy {
  public:
    int decideDamage(const CombatState& state) const override;
};

En el issue

El issue pide una tercera estrategia (“EstrategiaEscalable”) que hereda de la misma interfaz, igual que las otras dos. La diferencia real es que Standard y Alerted no guardan ningún dato propio (son objetos “sin memoria”, reutilizables para cualquier guardia), mientras que la nueva probablemente sí necesita guardar el nivel de alerta del guardia que la está usando — porque el daño depende de cuánto alertado está, no de un simple sí/no. Es una decisión de diseño real del equipo, no algo resuelto de antemano.

04

Recursión

Ejemplos/07_Recursion_Introduccion.cpp · Ejemplos/08_Recursion_Ejercicios.cpp · Material Practico → 03_recursividad

Una función recursiva es una función que se llama a sí misma con un problema más chico, hasta llegar a un caso base tan simple que no necesita más llamadas. 07_Recursion_Introduccion.cpp ya tiene el ejemplo canónico: imprimir un arreglo llamándose a sí misma con un elemento menos cada vez.

Ejemplos/07_Recursion_Introduccion.cpp
void impre(int v[], int n)
{
    // caso base: ya no queda nada más que imprimir
    if (n == 0) cout << v[n] << endl;
    else {
        // caso recursivo: resolvé el resto primero, con un problema más chico
        impre(v, n - 1);
        cout << v[n] << endl;
    }
}

Cada llamada que todavía no llegó al caso base queda “pendiente” en la pila de llamadas del programa (la call stack), esperando a que la llamada siguiente termine. Por eso una función recursiva sin caso base — o con un caso base al que nunca se llega — cuelga el programa: la pila crece para siempre.

El punto crítico de esta issue: el propio issue advierte que los guardias pueden estar conectados en círculo. Una recursión ingenua (“avisale a cada vecino, y ese avisale a los suyos”) daría vueltas eternamente en un círculo si no hay algo que corte la cadena.

En el issue

propagarAlerta(origen, nivel) es una función recursiva: un guardia recibe un nivel de alerta, se lo pasa a cada vecino con un nivel un escalón más bajo, y esos vecinos hacen exactamente lo mismo. El caso base no es “ya recorrí todos los guardias” — es la pregunta del propio diagrama del issue: “¿este nivel es mejor que el que el guardia ya tenía?”. Si no lo es, esa rama de la recursión termina ahí, sin seguir. Como el nivel baja un escalón en cada salto, hasta en un círculo cerrado la cadena eventualmente deja de mejorar lo que cada guardia ya tiene, y la recursión termina sola — sin necesitar una lista aparte de “guardias ya visitados”.

05

Grafos, como concepto

Vocabulario nuevo — no hay ejemplo previo en la carpeta del curso

Un grafo es, ni más ni menos, un conjunto de “nodos” conectados entre sí por “aristas”. Un guardia es un nodo; que un guardia pueda avisarle a otro es una arista. La fila de guardias del issue (“probado en una fila”) es el grafo más simple posible: cada nodo conectado solo con el siguiente. El caso “conectados en círculo” es el mismo tipo de estructura, pero donde el último nodo vuelve a conectar con el primero.

Analogía

Pensalo como un grupo de WhatsApp donde cada persona solo puede reenviar un mensaje a la gente que tiene agendada (sus “vecinos”), no a todo el grupo de una. Si A tiene agendado a B, y B tiene agendado a A, un mensaje puede rebotar A→B→A→B para siempre si nadie corta la cadena — exactamente el problema del círculo.

Cómo se ve el nivel de alerta “ondulando” hacia afuera desde el guardia que detectó al jugador, un escalón menos por cada salto:

guardia A (origen)nivel 3
→
vecino directonivel 2
→
vecino del vecinonivel 1
→
demasiado lejosnivel 0 (sin aviso)
Ojo con la palabra “grafo” en este repo: existe una estructura DirectedGraph en include/cybercba/structures/, pero el issue dice explícitamente que esa carpeta no se toca (además, por diseño del curso, esas cuatro estructuras están sin implementar todavía — son un ejercicio aparte). Acá se usa la idea de grafo — nodos con vecinos — no esa clase del repo.

En el issue

GuardSquad es, conceptualmente, un grafo: la lista de GuardSquadMember son los nodos, y la lista de vecinos de cada uno son sus aristas salientes. No hace falta ninguna clase especial de “grafo” para representar esto — alcanza con que cada guardia sepa quiénes son sus vecinos (ver sección 06) y con la función recursiva de la sección 04.

06

Un arreglo que crece solo (sin std::vector)

Ejemplos/10_Pilas_Arreglo.cpp · Ejemplos/11_Colas_Arreglo_Circular.cpp · include/cybercba/structures/DynamicArray.hpp (repo)

El proyecto prohíbe std::vector, std::array, std::map y los punteros inteligentes de la biblioteca estándar (std::unique_ptr, etc.) — es una decisión del curso para que programemos las estructuras nosotros, no para complicarnos la vida porque sí. Por eso el repo ya trae su propio arreglo dinámico, DynamicArray<T>, ya implementado y listo para usar. Esta sección explica qué problema resuelve y cómo funciona por dentro, paso a paso.

6.1El problema: un arreglo común no puede crecer

Un arreglo de toda la vida — int v[6], como en 10_Pilas_Arreglo.cpp — reserva un bloque de memoria de tamaño fijo en el momento en que se declara. Ese número no se negocia después: si declaraste v[6] y ya metiste 6 elementos, no existe un “v[6] = 7” que agrande el bloque. La memoria justo al lado de v casi seguro ya la está usando otra variable — no hay dónde “estirarse”.

La solución que ya viste en el curso para pilas y colas con arreglo es fijar un MAX grande de antemano y llevar un contador de cuántos lugares están realmente ocupados. Funciona, pero tiene un costo: si elegís un MAX chico, te quedás sin lugar; si elegís uno grande “por las dudas”, estás reservando memoria que capaz nunca usás. DynamicArray resuelve exactamente esto: no hay que adivinar un tamaño de antemano, el arreglo pide más memoria solo, cuando la necesita.

6.2Dos números, no uno: tamaño vs. capacidad

Esta es la idea que más cuesta al principio, porque un arreglo común tiene un solo número (su tamaño) y DynamicArray tiene dos, y son distintos a propósito:

  • m_size — cuántos elementos hay realmente guardados ahora mismo. Es lo que devuelve size().
  • m_capacity — cuántos elementos entrarían en el bloque de memoria actual antes de necesitar uno más grande. Es lo que devuelve capacity().

Siempre vale m_size <= m_capacity. La diferencia entre los dos son “lugares ya reservados pero todavía vacíos” — memoria de sobra guardada para que los próximos pushBack no tengan que pedir más memoria enseguida.

Notá el orden exacto: primero se pregunta “¿está lleno?”, y solo si la respuesta es sí se crece antes de guardar el nuevo elemento — nunca se guarda “de más” y se arregla después. Y notá también que crecer no es “agrandar lo que ya había”: es pedir memoria nueva, copiar, y recién ahí soltar la vieja. Por eso cualquier puntero o referencia (&arr[2], por ejemplo) que apuntaba a un elemento del bloque viejo queda apuntando a memoria que ya no existe apenas esto pasa — el propio DynamicArray.hpp lo deja documentado como parte del contrato de la clase. Es la sección 01 (punteros colgantes), pero ahora viéndola ocurrir en código real.

6.4¿Por qué duplicar la capacidad, y no sumar de a uno?

Podría parecer más “prolijo” crecer de a un lugar por vez (capacity + 1 en vez de capacity * 2) — total, es la misma idea. El problema es el costo total a lo largo de muchos pushBack:

  • Creciendo de a uno: casi todos los pushBack encontrarían el arreglo lleno, así que casi todos tendrían que copiar todo lo anterior. Para n elementos, eso es más o menos 1 + 2 + 3 + ... + n copias en total — una suma que crece como n². Con 1000 elementos, eso son del orden de 500.000 copias solo por el crecimiento.
  • Duplicando: los tamaños de bloque van 4, 8, 16, 32, ... — muy pocos crecimientos en total (unos log₂(n)), y aunque cada uno copie más elementos de una vez, la suma de todas las copias a lo largo de n pushes queda acotada por algo del orden de 2n — crece como n, no como n². Con 1000 elementos, del orden de 2000 copias en total.

Repartido entre los n pushes, eso significa que cada pushBack cuesta, en promedio, un trabajo constante — aunque de tanto en tanto uno puntual sea más caro porque le tocó disparar el crecimiento. A esta idea se la llama costo amortizado: no todos los pushes cuestan lo mismo, pero el promedio sobre muchos sí es barato.

6.6Ownership: por qué copiar y mover están escritos “a mano”

DynamicArray es dueño de su bloque de memoria: nadie más lo comparte, y por eso su destructor hace delete[] m_pBufferData — nadie más lo va a liberar. Ese dato es justo el que obliga a escribir el constructor de copia, el operador de copia, el constructor de movimiento y el operador de movimiento a mano (lo que en clase se conoce como la “regla de los cinco”):

  • Copiar (DynamicArray b = a;) tiene que reservar un bloque nuevo para b y copiar los valores adentro. Si en cambio b se quedara apuntando al mismo bloque que a (una “copia superficial”), el día que se destruyan los dos objetos, los dos destructores harían delete[] sobre la misma dirección de memoria — un “double free”, uno de los errores clásicos de memoria en C++.
  • Mover (cuando un DynamicArray se devuelve desde una función, por ejemplo) no necesita copiar nada: simplemente le “roba” el puntero al bloque al objeto de origen y deja a ese origen con nullptr. Es mucho más barato que copiar, y es seguro porque el origen queda en un estado válido para destruirse sin liberar nada (delete[] nullptr no hace nada).

Esto conecta directo con la sección 01: m_pBufferData es un puntero, y la regla de oro de esta clase es que nunca dos objetos DynamicArray apunten al mismo bloque a la vez — cada uno es dueño exclusivo del suyo.

En el issue

DynamicArray<T> ya está implementado y disponible — el issue no prohíbe usarlo, solo prohíbe modificar los archivos de structures/. Es la herramienta natural para dos cosas del issue: la lista de GuardSquadMember que vive adentro de GuardSquad, y la lista de vecinos (como índices, según la sección 01) que vive adentro de cada GuardSquadMember. Un detalle a tener en mente: si GuardSquad guarda sus miembros en un DynamicArray<GuardSquadMember>, cualquier pushBack que dispare un crecimiento (sección 6.3) reubica todos los miembros en memoria — otra razón más para que propagarAlerta trabaje con índices y no con referencias guardadas de antes.
