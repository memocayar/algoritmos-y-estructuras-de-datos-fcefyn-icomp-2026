Punteros

Base de todo lo que viene

Un árbol, un nodo de grafo, una lista enlazada: todos son, en el fondo, "una variable que guarda dónde está otra variable". Si esto no está claro, cualquier estructura con nodos se vuelve magia incomprensible.

La idea en una frase

Una variable normal guarda un dato. Un puntero guarda la dirección de memoria donde vive ese dato — no es el dato, es el mapa para llegar a él.

Qué tenés que tener claro

  • int x = 42; reserva una casilla de memoria y guarda 42 adentro.
  • int* p = &x; — el & significa "dame la dirección de". p guarda esa dirección, no el 42.
  • *p significa "el valor que está en la dirección que p guarda" (desreferenciar). *p = 100; cambia x, porque apuntan al mismo lugar.
  • Un puntero puede apuntar a nada válido: nullptr. Desreferenciarlo ahí (*p con p nulo) rompe el programa.
  • Aritmética de punteros: p + 1 no avanza 1 byte, avanza sizeof(tipo) bytes — te mueve al siguiente elemento del arreglo.
  • En structs con punteros, nodo->dato es exactamente lo mismo que (*nodo).dato: primero desreferenciás, después accedés al campo.
  • new reserva memoria en el heap que vive hasta que vos la liberás con delete (o hasta que termine el programa) — no se destruye sola al salir del scope.

Diagrama: qué pasa en memoria

Mirá la flecha: nace en p y termina en x. Esa flecha ES el puntero.

Ejemplo resuelto

int a = 5; int* p = &a; // p apunta a a *p = *p + 10; // "lo que hay en la dirección de p" += 10 std::cout << a; // ¿qué imprime?
Paso a paso: &a da la dirección de a, que p guarda. *p va a esa dirección y lee el valor (5), le suma 10, y lo vuelve a escribir en esa misma dirección. Como esa dirección ES donde vive a, a queda en 15. El puntero no copió el valor: te dio acceso directo a la casilla original.

Para memorizar

Mnemotecnia& = Address (¿dónde vive?) → te da la dirección.
* = "metete Ahí" (desreferenciar) → te da (o te deja cambiar) lo que hay en esa dirección.

Ejercicios rápidos

1. ¿Qué imprime este código?

int x = 7; int* p = &x; int* q = p; *q = 20; std::cout << x;
q se asigna como p, así que ambos guardan la misma dirección (la de x). Modificar *q modifica esa dirección — y x vive ahí.

2. Si p es int* y apunta al primer elemento de un arreglo de enteros, ¿qué hace p++?

La aritmética de punteros conoce el tipo al que apunta: avanza "una casilla del arreglo", no un byte literal.

3. ¿Por qué nodo->dato y (*nodo).dato son lo mismo?

-> es simplemente azúcar sintáctica: desreferenciar y acceder al miembro en un solo paso.

Ejemplo integrador: armando una lista a mano

struct NodoLista { int valor; NodoLista* siguiente; // puntero al próximo nodo (o nullptr si es el último) }; int main() { NodoLista* primero = new NodoLista{10, nullptr}; NodoLista* segundo = new NodoLista{20, nullptr}; NodoLista* tercero = new NodoLista{30, nullptr}; // 3 nodos creados en el heap con new primero->siguiente = segundo; // -> porque 'primero' es un puntero segundo->siguiente = tercero; // tercero->siguiente ya es nullptr: ahí termina la lista NodoLista* actual = primero; // 'actual' es un cursor que recorre la lista while (actual != nullptr) { std::cout << actual->valor << " "; // accedo al dato con -> actual = actual->siguiente; // avanzo: ahora actual apunta al siguiente } // imprime: 10 20 30 delete primero; delete segundo; delete tercero; // liberamos lo que creamos con new }
Este ejemplo junta todo lo de la sección: creás nodos en el heap con new (cada uno es un bloque de memoria aparte), los encadenás guardando en siguiente la dirección del próximo — por eso ->, porque primero y segundo son punteros — y después recorrés la lista con un puntero "cursor" (actual) que avanza de nodo en nodo. Ese patrón, "mientras no sea nullptr, procesar y avanzar al siguiente", es la base de casi cualquier recorrido de lista, árbol o grafo que vas a programar en la materia. Y como cada nodo se creó con new, hay que liberarlo con delete al final — si no, esa memoria queda reservada para siempre (memory leak).

Recursión

Sostiene Árboles y DFS

Casi todo "Árboles" en el segundo parcial (altura, factor de balance, búsquedas en BST) y DFS en grafos se resuelve con una función que se llama a sí misma. Si confiás en el patrón, dejás de necesitar "desenrollar" todo a mano.

La idea en una frase

Una función recursiva resuelve un problema resolviendo una versión más chica del mismo problema, hasta llegar a un caso tan simple que ya conoce la respuesta sin llamarse de nuevo.

Qué tenés que tener claro

  • Toda recursión necesita dos partes: caso base (frena la recursión) y caso recursivo (reduce el problema y llama de nuevo).
  • Cada llamada crea su propio "marco" en la pila de llamadas, con sus propias variables locales — no se mezclan entre sí.
  • No hace falta desenrollar todo mentalmente: confiá en que la llamada recursiva ya resuelve bien el subproblema más chico (el "salto de fe").
  • Si el caso base está mal, o nunca se alcanza, el programa explota con stack overflow (demasiados marcos apilados).
  • En árboles, el patrón casi siempre es: resolver(nodo) = combinar( resolver(izq), resolver(der) ), con "nodo == nullptr" como caso base.

Diagrama: la pila de llamadas en vivo

Ejemplo resuelto

int factorial(int n) { if (n == 0) return 1; // caso base return n * factorial(n-1); // caso recursivo }
Cómo leerlo sin desenrollar todo: no pienses "factorial(4) llama a factorial(3) que llama a..." de una. Preguntate solo dos cosas: (1) ¿cuándo para? → cuando n llega a 0. (2) ¿cómo uso el resultado de un problema más chico para armar el mío? → multiplico n por el factorial de n-1, que ya confío que está bien calculado. Usá el diagrama de arriba para ver la pila real paso a paso.

Para memorizar

MnemotecniaAntes de escribir una sola línea recursiva, respondé en voz alta: "¿Cuál es el caso más chico que ya sé resolver sin llamarme?" — esa es tu condición de corte. Todo lo demás es "resolvé el pedacito, y combiná con lo que ya resolviste antes".

Ejercicios rápidos

1. En esta función, ¿cuál es el caso base?

int alturaDe(NodoAVL* nodo) { if (nodo == nullptr) return 0; int izq = alturaDe(nodo->izquierdo); int der = alturaDe(nodo->derecho); return 1 + std::max(izq, der); }
Un árbol vacío (nullptr) no necesita llamarse de nuevo: ya sabés que su altura es 0. Ese es el límite donde la recursión deja de crecer.

2. ¿Qué pasaría si en factorial el caso base fuera if (n == 5) return 1; y lo llamás con factorial(3)?

n decrece desde 3, nunca va a tocar 5: la recursión nunca encuentra su caso base y sigue apilando llamadas hasta reventar la pila.

Ejemplo integrador: recursión sobre una estructura con punteros

struct NodoAVL { EstacionCritica dato; NodoAVL* izquierdo; NodoAVL* derecho; }; // cuenta cuántas estaciones del árbol tienen id menor que "limite" int contarMenoresA(NodoAVL* nodo, int limite) { if (nodo == nullptr) return 0; // caso base: árbol vacío, no suma nada int cuenta = (nodo->dato.id < limite) ? 1 : 0; // ¿este nodo cuenta? // caso recursivo: este nodo + lo que cuentan sus dos subárboles return cuenta + contarMenoresA(nodo->izquierdo, limite) + contarMenoresA(nodo->derecho, limite); }
Esta función mezcla recursión con punteros: para "entrar" a cada nodo usás -> (porque nodo es un puntero a NodoAVL), el caso base es el mismo patrón que vas a usar en casi todo Árboles (nodo == nullptr), y el caso recursivo no se llama una sola vez sino dos — una para el subárbol izquierdo y otra para el derecho — y suma los resultados. Esta es exactamente la forma de las funciones recursivas sobre árboles que te van a pedir en el parcial (altura, factor de balance, conteos por rango): un trabajito con el nodo actual + combinar lo que devuelven las llamadas recursivas a los hijos.

POO básica

El formato de TODOS los ejercicios del parcial

En el examen nunca partís de una hoja en blanco: siempre te dan una clase ya armada (como MetroNocturno o AgendaServicios) y vos completás 1-2 métodos adentro. Saber leer rápido qué es privado y qué es público te ahorra minutos clave.

La idea en una frase

Una clase es un plano que describe qué datos tiene un objeto y qué puede hacer. Un objeto es una instancia concreta construida a partir de ese plano.

Qué tenés que tener claro

  • private: solo lo pueden usar los propios métodos de la clase, desde adentro.
  • public: lo puede usar cualquiera que tenga un objeto de esa clase, desde afuera.
  • El constructor (mismo nombre que la clase) inicializa el objeto cuando se crea con new o por valor.
  • Un método definido fuera de la clase se escribe TipoRetorno NombreClase::nombreMetodo(...) { ... } — el :: dice "esto pertenece a esa clase".
  • Dentro de un método de la clase, tenés acceso directo a todos los atributos private de ese objeto (sin pedir permiso).
  • En el parcial: antes de escribir código, leé qué atributos privados ya existen (arreglos, contadores) — casi siempre ya tenés lo que necesitás, no hace falta inventar estructuras nuevas.

Diagrama: plano de clase → objetos

Rojo = solo accesible desde adentro de la clase. Verde = accesible desde cualquier lado que tenga el objeto.

Ejemplo resuelto

class MonitorAVL { private: NodoAVL* raiz; public: int factorBalanceDe(int estacionId); // lo vas a completar vos }; // fuera de la clase, implementando el método: int MonitorAVL::factorBalanceDe(int estacionId) { // ACÁ ADENTRO: "raiz" es visible aunque sea private, // porque este método PERTENECE a la clase. }
La trampa típica: el estudiante ve private y piensa "no lo puedo tocar". Pero dentro de un método de esa misma clase, sí podés — el private bloquea el acceso desde afuera (por ejemplo desde main()), no desde los propios métodos.

Para memorizar

MnemotecniaPrivate es tu diario íntimo: solo vos (los métodos de la clase) lo leés. Public es tu vidriera: cualquiera que pase por la calle (código externo) lo puede ver y usar.

Ejercicios rápidos

1. Dado NodoAVL* izquierdo; como atributo private, ¿desde dónde lo puedo usar directamente?

private restringe el acceso a "desde afuera de la clase", no a "desde ningún lado".

2. Te piden implementar int RedComponentes::tamanoComponenteOperativa(int origenId). ¿Qué es lo primero que tenés que mirar?

Casi siempre el enunciado ya te da (como private) exactamente los arreglos que necesitás: estaciones[], hayTunel[][], cantidadEstaciones. El trabajo es usarlos, no inventar de cero.

Ejemplo integrador: clase completa, :: , objetos por valor y por puntero

class Mochila { private: int capacidadMaxima; int pesoActual; public: Mochila(int capacidad) { // constructor: se ejecuta al crear el objeto capacidadMaxima = capacidad; pesoActual = 0; } bool agregarPeso(int peso); // declarado acá... int espacioLibre(); // ...implementado más abajo, fuera de la clase }; // "Mochila::" le dice al compilador: este método PERTENECE a la clase Mochila bool Mochila::agregarPeso(int peso) { if (pesoActual + peso > capacidadMaxima) return false; // no entra, está lleno pesoActual = pesoActual + peso; // accedo directo: estoy ADENTRO de la clase return true; } int Mochila::espacioLibre() { return capacidadMaxima - pesoActual; } int main() { Mochila mia(50); // objeto "por valor", vive en la pila Mochila* otra = new Mochila(30); // 'otra' es un PUNTERO a un objeto en el heap mia.agregarPeso(20); // objeto directo -> punto otra->agregarPeso(10); // puntero -> flecha std::cout << mia.espacioLibre(); // 30 std::cout << otra->espacioLibre(); // 20 delete otra; // se creó con new: hay que liberarlo a mano }
Acá están juntos los tres puntos que te generan dudas. (1) El :: aparece cuando separás la declaración de un método (adentro de la clase: agregarPeso(int peso);) de su implementación (afuera, como función aparte) — sin Mochila:: el compilador pensaría que agregarPeso es una función suelta sin relación con la clase; :: es literalmente "este método es DE esta clase". (2) Objeto por valor vs por puntero: mia es un objeto normal que vive en la pila y se accede con .; otra es un puntero a un objeto que vive en el heap (lo creaste con new) y se accede con ->. Las dos son Mochilas, solo cambia cómo las creaste y cómo las tocás. (3) Memoria: como otra se creó con new, en algún momento hay que hacer delete otra; — a mia no, porque se destruye sola al terminar main(). En el parcial casi siempre vas a estar del lado de "implementar el método con ::" y no del lado de crear objetos, pero entender los dos lados te ayuda a leer rápido el código que ya te dan.

Pilas y Colas

El concepto detrás de BFS

BFS (que vas a usar un montón en Grafos) ES, en el fondo, "meter cosas en una cola e ir sacando". Si tenés clarísima la diferencia entre pila y cola, entender BFS/DFS es gratis.

La idea en una frase

Pila (Stack): el último que entra es el primero que sale — LIFO. Cola (Queue): el primero que entra es el primero que sale — FIFO.

Qué tenés que tener claro

  • Pila: push (apila arriba), pop (saca de arriba), top (mira el de arriba sin sacarlo).
  • Cola: enqueue (entra por atrás), dequeue (sale por adelante), front (mira el primero sin sacarlo).
  • BFS usa una cola: explora "por capas" (todos los vecinos directos antes de ir más lejos) — por eso encuentra el camino más corto en un grafo sin pesos.
  • DFS se va lo más profundo posible antes de volver — se implementa con recursión (que internamente ya es una pila de llamadas) o con una pila explícita.
  • La cátedra tiene su propia Queue<TData> (no std::queue): memorizá su contrato — enqueue, dequeue, front(), isEmpty(), size().

Simulador: jugá vos con una Pila y una Cola

PILA (Stack) — entra y sale por el mismo extremo, arriba
pila vacía
COLA (Queue) — entra por atrás, sale por adelante
cola vacía

Ejemplo resuelto

Apilás: A, B, C → al desapilar sale: C, B, A (LIFO) Encolás: A, B, C → al desencolar sale: A, B, C (FIFO)
Por qué importa para BFS: si metés en la cola los vecinos de la estación actual, y siempre sacás por el frente, vas a procesar primero todas las estaciones a distancia 1, después todas las de distancia 2, etc. — nunca "te adelantás" a explorar algo lejano antes que algo cercano. Esa es la garantía de camino más corto de BFS.

Para memorizar

MnemotecniaPila = pila de platos: el último plato que pusiste arriba es el primero que sacás → LIFO.
Cola = cola del supermercado: el primero que se puso en la fila es el primero que se va → FIFO.

Ejercicios rápidos

1. Encolás, en este orden: Central, Neon, Docks. ¿En qué orden salen con dequeue?

FIFO: el primero que entra (Central) es el primero que sale.

2. ¿Por qué BFS garantiza el camino MÁS CORTO (en cantidad de tramos) y una búsqueda recursiva tipo DFS no?

DFS se mete por una rama hasta el fondo antes de probar otra — puede encontrar UN camino, pero no necesariamente el más corto. BFS, al procesar por capas, sí lo garantiza.

3. En el contrato de la cátedra, front() en la Queue<TData>...

Son dos pasos separados a propósito: mirar (front) y sacar (dequeue) — un error clásico es olvidarse de hacer dequeue() y quedar en loop infinito.

Ejemplo integrador: una Pila armada como clase, resolviendo un problema real

class Pila { private: int datos[100]; int cantidad; public: Pila() { cantidad = 0; } // constructor: arranca vacía void push(int valor) { datos[cantidad] = valor; cantidad++; } int pop() { cantidad--; return datos[cantidad]; } // saca el de arriba y lo devuelve int top() { return datos[cantidad - 1]; } // mira el de arriba SIN sacarlo bool estaVacia() { return cantidad == 0; } }; // clásico: ¿los paréntesis de un string están bien balanceados? bool parentesisBalanceados(std::string texto) { Pila pila; // objeto Pila "por valor" for (char c : texto) { if (c == '(') { pila.push(c); // abre un paréntesis: lo apilo } else if (c == ')') { if (pila.estaVacia()) return false; // cierra algo que nunca se abrió pila.pop(); // cierra: desapilo el ( que le corresponde } } return pila.estaVacia(); // si queda algo sin cerrar, no está balanceado }
Esta Pila es una clase como cualquier otra (constructor, métodos públicos, datos privados) — la diferencia es que la usás como herramienta en vez de modelar algo del mundo real. El truco de parentesisBalanceados es la aplicación más clásica de LIFO: cada vez que abrís un paréntesis lo "guardás" arriba de la pila, y cuando aparece uno que cierra, tiene que coincidir con el último que abriste — justo lo que pop() te devuelve. Si en algún momento querés cerrar y la pila ya está vacía, ese ) no tiene con qué emparejarse: no está balanceado. Este mismo patrón — "necesito deshacer en el orden inverso al que hice las cosas" — es la razón de fondo por la que DFS y la recursión misma funcionan con una pila por debajo.

Ordenamiento

Comparar e intercambiar, con método

Todos los algoritmos de ordenamiento hacen lo mismo en el fondo: comparar elementos e intercambiarlos. La diferencia entre ellos es CUÁNDO comparan y CUÁNTAS veces — de eso depende si son O(n²) o O(n log n).

La idea en una frase

Ordenar es ir dejando, paso a paso, cada elemento en su posición final — la diferencia entre algoritmos es la estrategia para decidir qué comparar en cada paso.

Qué tenés que tener claro

  • Selección: en cada pasada busca el MÍNIMO de lo que falta ordenar y lo manda al frente. Pocos intercambios, pero siempre compara todo.
  • Burbuja: recorre comparando VECINOS y los intercambia si están en el orden incorrecto — el mayor va "burbujeando" hacia el final en cada pasada.
  • Inserción: toma el próximo elemento y lo inserta en el lugar correcto dentro de la parte ya ordenada — como ordenar cartas en la mano. Rápido si los datos ya están casi ordenados.
  • Selección, Burbuja e Inserción son O(n²): simples de programar a mano, pero lentos para n grande.
  • Mergesort: divide el arreglo en mitades, ordena cada mitad por separado (recursión) y las MEZCLA ya ordenadas. Siempre O(n log n), pero usa memoria extra.
  • Quicksort: elige un pivote, separa menores/mayores a su alrededor, y ordena cada lado por recursión. Rápido en promedio (O(n log n)), pero si el pivote siempre es el peor posible, cae a O(n²).
  • Un ordenamiento es estable si dos elementos iguales mantienen su orden relativo original — importa cuando ordenás por más de un criterio (ej: por fecha, y después por nombre).

Fijate la diferencia con Selección: acá la zona "ya ordenada" (verde) crece desde la derecha, no desde la izquierda — porque cada pasada empuja el mayor hasta el final, en vez de traer el mínimo al frente.

Para memorizar

MnemotecniaSelección: elegís al campeón (mínimo) de lo que queda.
Burbuja: el más grande sube como burbuja, de a un lugar por vez.
Inserción: como ordenar cartas en la mano, insertando cada una donde corresponde.
Mergesort = divide y MEZCLA. Quicksort = divide por un PIVOTE.

Ejercicios rápidos

1. En burbuja, ¿qué se compara en cada paso?

Burbuja compara pares consecutivos y los intercambia si están desordenados — por eso el mayor "flota" hacia el final de a un paso.

2. ¿Cuál es la complejidad en el PEOR CASO de Quicksort, y cuándo pasa?

Si el pivote siempre queda en un extremo (peor elección posible), una de las dos particiones queda vacía y Quicksort degenera en un algoritmo O(n²), similar a selección.

3. Exam-style: tenés que ordenar un arreglo de 50 elementos CASI ya ordenado (solo 2 están fuera de lugar). ¿Qué algoritmo de los vistos conviene más y por qué?

Inserción es "adaptativo": su costo depende de cuánto desorden hay. Selección, en cambio, siempre hace la misma cantidad de comparaciones sin importar si los datos ya estaban ordenados.

Árboles (BST y AVL)

Recursión aplicada a buscar rápido

Un árbol binario de búsqueda (BST) organiza los datos para que buscar sea rápido. Un AVL es un BST que además se OBLIGA a quedarse equilibrado, para que esa velocidad no se arruine según el orden en que insertes.

La idea en una frase

En un BST, para todo nodo: lo que está a la izquierda es MENOR, lo que está a la derecha es MAYOR. Esa regla se repite en cada subárbol, nivel tras nivel.

Qué tenés que tener claro

  • Buscar en BST: comparás con la raíz; si es menor andás a la izquierda, si es mayor a la derecha, repetís — por eso buscar cuesta O(altura), no O(n).
  • El problema de un BST sin control: si insertás datos ya ordenados (1,2,3,4...), degenera en una lista — la altura se vuelve O(n) y perdés toda la ventaja.
  • Factor de balance de un nodo = altura(subárbol derecho) − altura(subárbol izquierdo). En un AVL válido, tiene que estar en {-1, 0, 1} para TODO nodo, sin excepción.
  • Si una inserción deja el factor de balance fuera de ese rango, el AVL hace una rotación para reequilibrarse — reorganiza punteros, pero sigue siendo un BST válido (el orden izquierda-menor/derecha-mayor no se rompe).
  • Altura de un árbol vacío (nullptr) se define como 0 (o a veces -1, según la cátedra) — leé siempre la convención exacta que te dan en el enunciado del parcial.
  • Para contar/buscar en un RANGO de valores (ej: "cuántos nodos entre 10 y 50"), podés podar ramas enteras: si el valor del nodo ya descarta un subárbol completo por la propiedad BST, ni siquiera lo visitás.
  • Operaciones básicas que tenés que saber de memoria: insertar (recursivo, devuelve el puntero del subárbol ya con el nuevo nodo), size/height (recursivos, 1 + recursión en ambos hijos), contains (igual que buscar), min/max (bajar siempre por izquierda o siempre por derecha), inorden (izquierda → nodo → derecha, da el árbol ordenado).
  • Patrón muy común en el parcial: un ABB donde cada nodo guarda OTRA estructura adentro (una Lista, Pila o Cola) — ej: un árbol de máquinas donde cada una tiene una Lista de intervenciones, o un árbol de productos con una Pila de cambios para poder "deshacer". El método primero busca el NODO (no solo el dato) con un helper tipo buscarNodo(clave), y después opera sobre la estructura interna de ese nodo.

Ejemplo resuelto: las operaciones básicas, todas juntas

template <class T> Nodo<T>* ABB<T>::insertarRec(Nodo<T>* p, const T& x) { if (p == nullptr) return new Nodo<T>(x); // caso base: acá va el nuevo nodo if (x < p->dato) p->izq = insertarRec(p->izq, x); // menor → izquierda else if (p->dato < x) p->der = insertarRec(p->der, x); // mayor → derecha return p; // si es igual, no hace nada (sin duplicados) } template <class T> int ABB<T>::tamRec(const Nodo<T>* p) const { if (p == nullptr) return 0; return 1 + tamRec(p->izq) + tamRec(p->der); // este nodo + sus dos subárboles } template <class T> const Nodo<T>* ABB<T>::minNode(const Nodo<T>* p) const { if (p->izq == nullptr) return p; // no hay nada más chico: este es el mínimo return minNode(p->izq); // si hay izquierda, el mínimo está ahí } template <class T> void ABB<T>::inordenRec(const Nodo<T>* p, std::vector<T>& out) const { if (p == nullptr) return; inordenRec(p->izq, out); // primero todo lo menor out.push_back(p->dato); // después este nodo inordenRec(p->der, out); // después todo lo mayor }
Fijate que todas comparten la misma forma: caso base p == nullptr, y la "interesante" sucede combinando lo que devuelven las llamadas a los hijos. insertarRec es la única que DEVUELVE el puntero del nodo (para reconectar el árbol a medida que la recursión vuelve); las demás solo acumulan o comparan. minNode no compara nada — el mínimo de un BST siempre es "lo más a la izquierda posible", así que simplemente bajás por izquierda hasta que no haya más. inordenRec es el único patrón de la materia donde el ORDEN de las 3 líneas (izquierda, nodo, derecha) importa tanto: cambiarlo rompe que la salida quede ordenada.

Diagrama: recorrido de búsqueda en un BST

Buscamos el 40 en este BST. Mirá cómo en 3 pasos llegamos, sin visitar los otros 4 nodos.

Ejemplo resuelto

int MonitorAVL::alturaDe(NodoAVL* nodo) { if (nodo == nullptr) return 0; // caso base return 1 + std::max(alturaDe(nodo->izquierdo), alturaDe(nodo->derecho)); } int MonitorAVL::factorBalanceDe(NodoAVL* nodo) { if (nodo == nullptr) return 0; return alturaDe(nodo->derecho) - alturaDe(nodo->izquierdo); // derecha - izquierda }
Las dos funciones comparten el mismo patrón recursivo de la sección de Recursión: caso base nodo == nullptr, y caso recursivo que combina los dos subárboles. factorBalanceDe ni siquiera recorre el árbol de nuevo "a mano" — reutiliza alturaDe sobre cada hijo y resta. Si el resultado es mayor a 1 o menor a -1, ese nodo necesita una rotación.

Para memorizar

MnemotecniaBST: izquierda MENOS, derecha MÁS.
AVL: pensalo como una balanza — factor de balance fuera de [-1, 0, 1] significa que un lado pesa demasiado más que el otro, y hay que mover peso (rotar) para equilibrarla.

Ejercicios rápidos

1. Un nodo tiene subárbol izquierdo de altura 2 y subárbol derecho de altura 4. ¿Cuál es su factor de balance, y es válido en un AVL?

factorBalance = altura(derecho) - altura(izquierdo) = 4 - 2 = 2. Al estar fuera de [-1,0,1], ese nodo rompe la propiedad AVL.

2. ¿Por qué insertar 1,2,3,4,5 en orden en un BST normal (sin balanceo) es el peor caso posible?

Sin ningún valor menor que obligue a ramificar hacia la izquierda, el árbol crece en línea recta hacia la derecha — altura O(n), se pierde toda la ventaja de búsqueda O(log n).

3. Exam-style: ¿qué hace esta función?

int contar(NodoAVL* nodo, int min, int max) { if (nodo == nullptr) return 0; int cuenta = (nodo->dato.id >= min && nodo->dato.id <= max) ? 1 : 0; if (nodo->dato.id > min) cuenta += contar(nodo->izquierdo, min, max); if (nodo->dato.id < max) cuenta += contar(nodo->derecho, min, max); return cuenta; }
Los if antes de cada llamada recursiva son la poda: si el nodo actual ya es ≤ min, no tiene sentido mirar su subárbol izquierdo (todo ahí es aún menor); si ya es ≥ max, no hace falta mirar el derecho. Así evita visitar nodos que la propiedad BST ya garantiza que están fuera de rango.

Ejemplo integrador: conteo por rango, al estilo del examen

struct ServicioTren { int codigoTren; int minutoSalida; int anden; }; // cuenta cuántos servicios salen entre 'desde' y 'hasta' (inclusive), podando int AgendaServicios::contarEnVentanaRec(NodoAgenda* nodo, int desde, int hasta) { if (nodo == nullptr) return 0; // caso base: subárbol vacío int cuenta = 0; if (nodo->dato.minutoSalida >= desde && nodo->dato.minutoSalida <= hasta) cuenta = 1; // ¿este nodo entra en la ventana? // poda: solo bajo a la izquierda si todavía puede haber algo >= desde ahí if (nodo->dato.minutoSalida > desde) cuenta += contarEnVentanaRec(nodo->izquierdo, desde, hasta); // poda: solo bajo a la derecha si todavía puede haber algo <= hasta ahí if (nodo->dato.minutoSalida < hasta) cuenta += contarEnVentanaRec(nodo->derecho, desde, hasta); return cuenta; } int AgendaServicios::cantidadServiciosEnVentana(int desde, int hasta) { return contarEnVentanaRec(raiz, desde, hasta); // arranca la recursión desde la raíz privada }
Esta es la forma exacta en que te van a pedir "contar algo en un rango" en el parcial. Fijate que integra TODO lo que ya sabés: recursión con caso base nullptr, acceso por puntero (nodo->dato, nodo->izquierdo), y un método público corto (cantidadServiciosEnVentana) que solo le pasa la posta a uno privado recursivo (contarEnVentanaRec) agregando el parámetro nodo que la recursión necesita pero la firma pública no expone. La parte que marca la diferencia entre "funciona" y "es eficiente" son los dos if antes de cada llamada recursiva — sin ellos, la función seguiría dando el resultado correcto, pero visitaría el árbol ENTERO en vez de podar las ramas que ya sabés que no pueden tener nada útil.

Ejemplo integrador: un ABB donde cada nodo "tiene" otra estructura adentro

struct Cambio { int codigo; int precioAnterior; }; struct Producto { int codigo; int precio; }; // el ABB se ordena por 'codigo' // deshace el último cambio de precio: saca de la pila y restaura el precio bool CatalogoPrecios::deshacer(Pila<Cambio>& cambios) { if (cambios.isEmpty()) return false; // no hay nada que deshacer Cambio ultimo = cambios.top(); // miro el más reciente, sin sacarlo todavía cambios.pop(); // ahora sí lo saco de la pila Nodo<Producto>* nodo = buscarNodo(ultimo.codigo); // ① busco el NODO (no solo el dato) en el ABB nodo->dato.precio = ultimo.precioAnterior; // ② modifico el dato de ESE nodo puntual return true; }
Este es el patrón "compuesto" que apareció una y otra vez en la ejercitación real: el ABB no es la estructura principal del problema, es el índice que te deja encontrar rápido (por código) al elemento que en realidad querés modificar. La lógica tiene siempre dos partes separadas: ① usar el ABB para ubicar el nodo correcto (acá con un buscarNodo que, a diferencia de un `buscar` de solo lectura, te devuelve el puntero al nodo real para poder modificarlo), y ② operar sobre la OTRA estructura que vive adentro de ese nodo (acá una Pila de cambios, en otros ejercicios una Lista o una Cola) usando exactamente las operaciones que ya viste en Pilas y Colas (top, pop, isEmpty). Nunca se te pide reinventar el ABB ni la Pila — se te pide combinarlos.

Grafos

BFS, DFS y Dijkstra

Un grafo es un conjunto de nodos conectados entre sí, sin la jerarquía de un árbol — cualquier nodo puede conectarse con cualquier otro, y puede haber ciclos. BFS, DFS y Dijkstra son tres formas distintas de recorrerlo, cada una para un objetivo distinto.

La idea en una frase

BFS explora por capas con una cola (camino más corto en cantidad de aristas). DFS se mete lo más profundo posible antes de volver. Dijkstra busca el camino de menor costo total, no de menos pasos.

Qué tenés que tener claro

  • BFS usa la Queue<TData> de la cátedra (vista en Pilas y Colas) — encola vecinos no visitados y los procesa en el orden en que entraron.
  • SIEMPRE hay que marcar nodos como visitados en BFS/DFS — si no, en un grafo con ciclos el algoritmo entra en loop infinito.
  • DFS se implementa recursivo (o con pila explícita) — sirve para contar componentes conexas, detectar ciclos, explorar caminos completos.
  • Dijkstra encuentra el camino de menor costo (no menor cantidad de aristas) en un grafo con pesos NO negativos.
  • La cátedra pide Dijkstra con ARRAYS fijos, sin priority_queue ni STL: un array distancia[] (infinito salvo el origen en 0) y un array visitado[].
  • Patrón de Dijkstra "a mano", repetido N veces: (1) buscar a mano el no visitado con menor distancia, (2) marcarlo visitado, (3) "relajar" sus vecinos — si pasar por él da una distancia menor, actualizarla.
  • Contar componentes conexas con DFS: recorrés todos los nodos; cada vez que encontrás uno no visitado, hacés un DFS completo desde ahí (una componente) y contás cuántas veces arrancaste un DFS nuevo.

Diagrama: BFS paso a paso (con la cola en vivo)

cola (Queue<TData>)
BFS desde A. Mirá cómo la cola crece con los vecinos nuevos y se vacía en el orden en que entraron.

Ejemplo resuelto

bool RedSegura::existeRutaSegura(int origenId, int destinoId) { bool visitado[cantidadEstaciones] = {false}; Queue<int> cola; cola.enqueue(origenId); visitado[origenId] = true; while (!cola.isEmpty()) { int actual = cola.front(); // miro el primero, sin sacarlo cola.dequeue(); // ahora sí lo saco if (actual == destinoId) return true; // ¡llegué! for (int vecino = 0; vecino < cantidadEstaciones; vecino++) { if (hayConexion[actual][vecino] && !visitado[vecino]) { visitado[vecino] = true; // marco ANTES de encolar cola.enqueue(vecino); } } } return false; // vacié la cola y nunca llegué }
El detalle que marca la diferencia entre "funciona" y "bug": visitado[vecino] = true se hace antes de encolar, no después de desencolar. Si lo hicieras después, el mismo vecino podría entrar a la cola varias veces (por distintos caminos) antes de que ninguno lo marque como visitado — multiplicando trabajo innecesario, aunque el resultado final siga siendo correcto.

Para memorizar

MnemotecniaBFS = ondas en el agua: explora por capas de distancia, con una cola.
DFS = laberinto siguiendo siempre la pared: se mete al fondo antes de retroceder.
Dijkstra sin priority_queue: "buscar el mínimo a mano, marcarlo, relajar vecinos — repetir N veces."

Ejercicios rápidos

1. ¿Por qué BFS garantiza el camino con MENOS aristas, y Dijkstra no busca eso sino el de MENOR costo?

Un camino de 3 aristas con pesos [1,1,1] (costo 3) puede ser peor que uno de 4 aristas con pesos [1,1,1,0] (costo 3 también) o incluso mejor que uno de 2 aristas con pesos [10,10]. BFS ignora el peso; Dijkstra lo usa.

2. En DFS recursivo para contar componentes conexas, ¿qué pasa si te olvidás de marcar visitada[actual] = true antes de llamar recursivamente a los vecinos?

Sin marcar visitado ANTES de explorar vecinos, un ciclo en el grafo (A-B-C-A) hace que el DFS vuelva a entrar en A una y otra vez — exactamente el mismo problema de "caso base que nunca se alcanza" que vimos en Recursión.

3. Exam-style: tenés distancia[] inicializado en COSTO_INFINITO salvo el origen (0), y visitado[] en falso. ¿Cuál es el primer paso de cada iteración de Dijkstra "a mano"?

Sin priority_queue, ese "elegir el mínimo" se hace con un bucle que recorre todo el array distancia[] buscando el no-visitado más chico — es el reemplazo manual de lo que una cola de prioridad haría automático.

Ejemplo integrador: Dijkstra con arrays, al estilo del examen

const int COSTO_INFINITO = 999999; // camino de menor costo total de energía entre dos estaciones int MetroNocturno::costoMinimoEnergia(int origenId, int destinoId) { int distancia[cantidadEstaciones]; bool visitado[cantidadEstaciones] = {false}; for (int i = 0; i < cantidadEstaciones; i++) distancia[i] = COSTO_INFINITO; distancia[origenId] = 0; // el origen cuesta 0 llegar a sí mismo for (int iter = 0; iter < cantidadEstaciones; iter++) { // 1) buscar a mano el no visitado con menor distancia int actual = -1; for (int i = 0; i < cantidadEstaciones; i++) { if (!visitado[i] && (actual == -1 || distancia[i] < distancia[actual])) actual = i; } if (distancia[actual] == COSTO_INFINITO) break; // lo que queda es inalcanzable visitado[actual] = true; // 2) marcarlo visitado // 3) relajar vecinos: ¿pasar por 'actual' mejora su distancia? for (int vecino = 0; vecino < cantidadEstaciones; vecino++) { if (costoTramo[actual][vecino] > 0 && !visitado[vecino]) { int nuevaDist = distancia[actual] + costoTramo[actual][vecino]; if (nuevaDist < distancia[vecino]) distancia[vecino] = nuevaDist; } } } return distancia[destinoId]; }
Memorizá esta función como tres bloques que se repiten N veces, exactamente como dice el checklist: buscar el mínimo no visitado (bucle 1), marcarlo (una línea), relajar sus vecinos (bucle 2, actualizando distancia[] solo si mejora). El if (distancia[actual] == COSTO_INFINITO) break; es un detalle fino pero importante: corta el algoritmo apenas ya no quedan nodos alcanzables, en vez de seguir iterando sobre infinitos sin sentido.

Otras Estructuras de Datos

Hash, Set, Heap y Bitset

Cada una de estas estructuras existe para resolver UN problema puntual mejor que las que ya conocés: buscar rapidísimo sin importar el orden (Hash), saber si algo "está o no" sin duplicados (Set), encontrar siempre el máximo/mínimo rápido (Heap), o guardar millones de sí/no gastando el mínimo de memoria (Bitset).

La idea en una frase

Estas estructuras no reemplazan a las anteriores — las complementan, cada una optimizada para UNA operación puntual: buscar por clave, chequear pertenencia, obtener el máximo, o ahorrar memoria bit a bit.

Qué tenés que tener claro

  • Hash table: una función hash convierte una clave en un índice de array — buscar/insertar es O(1) EN PROMEDIO, sin importar cuántos elementos haya.
  • Colisión: cuando dos claves distintas dan el mismo índice hash. Se resuelve con encadenamiento (cada casilla guarda una lista) o direccionamiento abierto (buscás la siguiente casilla libre).
  • Un Set es, en esencia, un Hash (o un árbol balanceado) donde solo importa SI un elemento está, no un valor asociado — nunca tiene duplicados.
  • Heap (montículo): un árbol casi-completo donde cada padre es ≥ sus hijos (max-heap) o ≤ sus hijos (min-heap) — la propiedad se cumple SOLO entre padre e hijo directo, no entre hermanos.
  • En un max-heap representado como array, el padre de la posición i está en (i-1)/2, y sus hijos en 2i+1 y 2i+2 — sin necesitar punteros.
  • Bitset: un array donde cada casilla ocupa literalmente UN BIT, no un byte ni un int — para guardar millones de sí/no gastando 8x (o más) menos memoria que bool[].
  • Por qué importa en grafos grandes: marcar "visitados" con bool visitado[] gasta 1 byte por nodo; con un bitset gastás 1 bit — 8 veces menos memoria para la misma información.

Ejemplo resuelto

struct Celda { int clave; int valor; Celda* siguiente; }; // encadenamiento: cada casilla es una lista int hash(int clave, int tamanioTabla) { return clave % tamanioTabla; // función hash simple: resto de la división } void insertar(Celda* tabla[], int tamanioTabla, int clave, int valor) { int idx = hash(clave, tamanioTabla); Celda* nueva = new Celda{clave, valor, tabla[idx]}; // la nueva apunta a lo que ya había tabla[idx] = nueva; // la casilla ahora empieza con la nueva }
Fijate que insertar no sobreescribe tabla[idx] — lo usa como siguiente de la celda nueva, y después hace que tabla[idx] apunte a la nueva. Es exactamente el mismo patrón de "insertar al comienzo de una lista enlazada" que viste en Punteros, solo que acá la lista vive DENTRO de una casilla del array — así es como el encadenamiento resuelve colisiones: dos claves con el mismo idx conviven en la misma lista, en vez de pisarse.

Para memorizar

MnemotecniaHash = la libreta de teléfonos mágica: no buscás letra por letra, la función hash te dice directo en qué página mirar.
Heap = el podio: el máximo siempre está arriba de todo, pero el resto no está necesariamente ordenado entre sí.
Bitset = la misma info, pero exprimida: 8 preguntas sí/no en el espacio de UN byte.

Ejercicios rápidos

1. ¿Por qué buscar en una hash table es O(1) en promedio, y no O(n) como en una lista?

La función hash calcula el índice en tiempo constante — en el caso ideal (sin colisiones) vas directo a la casilla, sin comparar contra los demás elementos.

2. Exam-style (MCQ real): ¿cuál de estas afirmaciones sobre un max-heap es correcta?

La propiedad de heap es LOCAL (padre vs. sus hijos directos), no global como en un BST. Por eso un heap no sirve para buscar un valor cualquiera en O(log n) — solo garantiza que el máximo está en la raíz.

3. Exam-style (MCQ real): ¿por qué conviene usar bitset en vez de vector<bool> o un array de bool para marcar nodos visitados en un grafo con millones de nodos?

La ventaja de bitset es específicamente de MEMORIA, no de velocidad algorítmica: con millones de nodos, pasar de 1 byte a 1 bit por nodo puede ser la diferencia entre que el programa entre en memoria o no.

Ejemplo integrador: tabla hash completa con búsqueda

struct Celda { int clave; int valor; Celda* siguiente; }; class TablaHash { private: Celda* tabla[101]; // 101: número primo, reduce colisiones int hash(int clave) { return clave % 101; } public: TablaHash() { for (int i = 0; i < 101; i++) tabla[i] = nullptr; } // todas vacías al inicio void insertar(int clave, int valor) { int idx = hash(clave); tabla[idx] = new Celda{clave, valor, tabla[idx]}; // inserto al INICIO de la lista de esa casilla } bool buscar(int clave, int& valorEncontrado) { int idx = hash(clave); Celda* actual = tabla[idx]; // voy a recorrer SOLO la lista de esta casilla while (actual != nullptr) { if (actual->clave == clave) { valorEncontrado = actual->valor; return true; // encontrado } actual = actual->siguiente; // mismo patrón "cursor" de Punteros } return false; // recorrí toda la lista de esa casilla y no estaba } };
Esta clase junta todo: private/public y constructor de POO, punteros y new para armar la lista de cada casilla, y el patrón "cursor que avanza con actual = actual->siguiente" que ya viste en Punteros. La diferencia clave con una lista enlazada común es que acá buscar() nunca recorre TODOS los elementos de la tabla — el hash ya te ubicó en la casilla correcta, y while solo recorre los pocos elementos que colisionaron ahí (idealmente, uno o ninguno).
